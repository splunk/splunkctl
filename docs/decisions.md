# Design Decisions

Decisions that are non-obvious or that have come up during development. Useful context for agents modifying the code.

---

## object verb command shape (not verb object)

`splunkctl index list`, not `splunkctl list index`.

Resource-first is better for LLM agent discoverability: `splunkctl index --help` shows everything you can do with an index in one call. An agent exploring the CLI can enumerate objects first, then drill into verbs.

The legacy `splunk` binary uses `splunk list index`. We are not a compatibility shim; the difference is intentional.

---

## Token-only auth (no username/password)

Authentication never prompts, so a token can be injected through `SPLUNKCTL_TOKEN` without user interaction.
The separate write-safety check uses terminal detection when it asks a human to confirm a potentially state-changing operation.

---

## Codegen from XML, not from REST API discovery

The Splunk REST API doesn't have a machine-readable introspection endpoint that maps cleanly to CLI commands. `splunkrc_cmds.xml` is the canonical definition of what the `splunk` CLI supports via REST — it contains URIs, argument names, help text, and verb→method mappings. Generating from it means our CLI surface stays aligned with the official Splunk CLI surface.

---

## Emitted generated object files are committed to the repo

Object files carrying the standard `// Code generated by splunkctl codegen. DO NOT EDIT.` header are committed rather than ignored. They are human-readable Go code that can be grepped, reviewed in MR diffs, and understood without running the generator. `cmd/generated/shared.go`, `_test.go` files, and `.gitkeep` are also committed, but they are hand-maintained rather than generator output. The generator is a build tool, not a runtime dependency.

---

## internal/cmdctx to break the import cycle

`cmd` needs to register `cmd/generated` commands onto `rootCmd`. `cmd/generated` needs to call the client that lives in `cmd` context. If `cmd/generated` imported `cmd`, we'd have a cycle.

`cmd` imports `cmd/generated` to register generated commands on the root. `cmd/generated` must not import `cmd`, because that back-edge would create the cycle. `internal/cmdctx` owns the context keys and helpers for the client and write check; both packages use it to share command dependencies without introducing the forbidden back-edge, and it imports `internal/client`.

Alternative considered: store the client in a package-level var in a shared package. Rejected because it's not goroutine-safe and makes tests harder (would need reset between tests).

---

## output.WithWriter for test injection

Tests cannot easily redirect `os.Stdout` (which would require `os.Pipe` and goroutines). For structured resource and REST results, `output.WithWriter(ctx, w)` stores a writer in the command context and lets tests capture `output.Print(cmd.Context(), ...)` output in a `bytes.Buffer`.

Raw or fixed-format responses, interactive prompts, and progress displays may intentionally use tested Cobra writers or an established terminal-specific path instead. `output.WithWriter` enables OS-independent capture for the structured-output path; it is not the capture mechanism for every command contract.

---

## no_client skips only client initialization

Commands like `version`, `schema`, `config get`, and `skill list` don't talk to Splunk.
If client initialization ran for every command, these workflows would unnecessarily require `--host` and `--token`.

The `Annotations["no_client"] = "true"` pattern skips client initialization for specific commands.
The root still installs write safety because offline commands can modify local state.

---

## RawDo vs Do on the client

`Do()` normalizes the Splunk Atom JSON feed into `[]map[string]any`. This works for 95% of commands. But for `search`, the response to `/search/jobs` is just `{"sid":"..."}`, not an Atom feed. And job results come back as `{"results":[...]}`, not `{"entry":[...]}`.

`RawDo()` returns raw bytes for callers that need to parse the response themselves. It still handles auth headers and `output_mode=json`, but doesn't interpret the body.

---

## PathVarPlaceholder in generator (not regex at runtime)

Some REST URIs have `{name}` in the middle (e.g. `/data/indexes/{name}/enable/`). At generation time, we know the exact placeholder string. Rather than embedding a regex in each generated command, we emit a direct `strings.ReplaceAll(path, "{name}", resourceID)`. This keeps generated code simple and avoids a runtime `regexp` import in every generated file.

---

## 30s HTTP timeout

No timeout = agent hangs indefinitely on unreachable hosts. 30s is long enough for slow Splunk instances on high-latency networks; short enough to give agents a useful error within the typical agent step timeout window.

---

## SplunkError exported from internal/client

`cmd/root.go` needs to type-assert on `SplunkError` to map error codes to exit codes. Since `cmd` imports `internal/client`, the type just needs to be exported from that package. No separate error package needed.

---

## example rewriting in codegen

The XML examples use the old `./splunk verb object` format. Rewriting at generation time (in `codegen/generator.go:rewriteExample`) means:
1. Generated help text shows correct `splunkctl object verb` examples
2. Agents reading `--help` see commands they can actually run

The rewrite is imperfect for complex examples (multi-flag, pipes) but catches the common `./splunk verb obj` pattern.

---

## Remote Splunk app installation

`splunkctl app install` can install an app from a file path on the remote Splunk
server. The file must already exist on that server — splunkctl does not upload or
transfer the archive itself.

This is because Splunk's REST API (`POST /services/apps/local`) does not accept a
file upload stream or a remote URL as input. When `filename=true` is passed,
Splunk reads the archive directly from its own filesystem. The client (splunkctl)
is therefore responsible for getting the file onto the server before calling
install.

**Required steps:**

1. Get the `.tgz` archive onto the remote Splunk server. Two common approaches:
   - **SCP** — copy from your local machine:
     ```
     scp app.tgz user@splunk-host:/tmp/app.tgz
     ```
   - **wget** — download directly on the remote server (SSH in first):
     ```
     wget -O /tmp/app.tgz https://example.com/app.tgz
     ```
2. Ensure the archive is readable by the `splunk` process. Prefer transferring
   ownership to the `splunk` user rather than making the file world-readable:
   ```
   chown splunk:splunk /tmp/app.tgz
   ```
   If you cannot change ownership, `chmod 644` makes the file world-readable as
   a fallback, but note this exposes the archive to all local users on the server.
3. Run the install using the server-side path:
   ```
   splunkctl app install /tmp/app.tgz
   ```
   splunkctl sends `filename=true` to the Splunk REST API, which tells Splunk to
   read the archive from its own filesystem.

**Why URL-based install is not supported.**
Splunk's REST API does not fetch remote URLs. Passing a URL as the app name to
`POST /services/apps/local` causes Splunk to treat the URL string as an app
folder name and reject it with a 400 error because URLs contain special
characters. A separate endpoint (`/services/apps/appinstall`) that might suggest
URL support does not exist on Splunk 10.3.x or 10.4.x (validated by querying
`/services/apps` — only `local` and `apptemplates` are exposed). The workaround
is to download the archive onto the remote server first using `wget` or `scp`,
set the required permissions, and then install using the server-side path as
described above.

---

## filename=true for file-path app installs (not multipart upload)

`splunkctl app install <path>` sends `filename=true` in the POST body rather than uploading the file bytes as multipart. Splunk then reads the archive from its own filesystem. Multipart upload is blocked by Splunk Cloud WAF and is not a supported path.

The archive must exist on the Splunk server's filesystem. In CI, `orca_service.py` stages the test archive via `scp` before tests run.

---

## URL-based app install is not supported

`isFilePath()` does not match `http://` or `https://` — a URL argument falls through to the plain-name code path. The Splunk REST API does not fetch remote URLs, so passing one returns an error from Splunk. URL support would require client-side download logic before the install call; this is outside the intended scope.

---

## NeedsStrings conditional import in template

Generated files that have no path templates don't need `import "strings"`. Go refuses to compile with unused imports. Adding `strings` unconditionally to every generated file would add a lint violation in 90% of files. The `NeedsStrings bool` field on `GeneratedFile` lets the template conditionally emit the import.

---

## Write safety is enforced at effect boundaries

Remote operations are checked from the shared client immediately before any HTTP method other than GET, HEAD, or OPTIONS reaches the network.
Local operations call the same invocation-scoped check immediately before their first state change.
This avoids maintaining a command-name catalog and automatically covers new REST commands that use the client.
The conservative HTTP rule can block a read-oriented Splunk endpoint implemented with POST; adding endpoint-name exceptions would weaken the simple fail-closed boundary.

## GitLab is canonical; GitHub is an allowlisted projection

Changes are reviewed and merged in GitLab. GitHub receives selected source and
documentation paths through the GitLab pipeline; it is not a bidirectional Git
mirror, so publication commits have different commit IDs from their GitLab
sources.

Packaging reads the committed Git objects,
not mutable runner files. Validation produces a checksummed candidate and exact
GitHub diff. Publishing is a serialized manual action from a protected GitLab
tag, verifies both repositories have not moved, pushes the tag-specific
`gitlab-release/<tag>` publication branch, and opens a PR into protected GitHub
`main`.
GitHub-only paths outside the managed roots are intentionally preserved.

A native push mirror was rejected because it cannot publish only selected paths
or keep private GitLab files out of the public repository. A bidirectional
sync was rejected because it would create two competing sources of truth.
