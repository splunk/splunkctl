# Code Generator

> **External prerequisite:** `splunkrc_cmds.xml` is the authoritative generator input, but it is not included in a standalone `splunkctl` checkout. Regeneration requires the compatible file from the matching splcore source revision.

## What it does

The generator reads `splunkrc_cmds.xml` (the authoritative source for Splunk's REST-backed CLI surface) and writes one Go file for each eligible XML `<item>` object into `cmd/generated/`. It skips item aliases/synonyms, items without a common or command URI, items with a same-name override file, and items left with no eligible verbs.

Each emitted file contains:
- A top-level `XxxCmd` Cobra command for the object
- One sub-command per eligible XML `<cmd>` element
- An `init()` that registers sub-commands and declares flags

Within an item, command aliases, empty command names, and commands without an effective per-command or common URI are skipped. The generator writes eligible files but never deletes files that are no longer eligible.

## Running the generator

### Explicit-input repository-root workflow

Source `splunkrc_cmds.xml` from the matching or otherwise compatible splcore source revision. Record the immutable source revision and the XML file's SHA-256 digest in the MR; do not substitute an arbitrary XML revision.

From the `splunkctl` repository root, pass that input explicitly:

```bash
xml_path="REPLACE_WITH_STABLE_RELATIVE_XML_PATH"
go run ./codegen/ "$xml_path" \
    ./codegen/templates/command.go.tmpl \
    ./cmd/generated/
```

Set `xml_path` to a concrete, stable, non-sensitive path relative to the repository root, then keep that value unchanged for both generator runs. The quoted `REPLACE_WITH_...` value is a shell-safe template and is not literal execution evidence. `codegen/main.go` assigns the exact XML argument to `XMLSource`, and the template embeds it verbatim as `// Source: ...` in every emitted file. An arbitrary absolute path can therefore churn every generated header and expose workstation details. Preserve the current relative label `../../cfg/bundles/default/static/splunkrc_cmds.xml` when the checkout layout permits; otherwise choose a reproducible relative label that resolves from the repository root. Record the resolved label and actual command form alongside the immutable source revision and SHA-256 digest.

### Layout-dependent convenience commands

The `//go:generate` directive in `main.go` hard-codes this input path:

```text
../../cfg/bundles/default/static/splunkrc_cmds.xml
```

Consequently, both convenience commands assume the documented splcore-integrated layout, with this checkout at `tools/splunkctl/` and a compatible XML file in the matching splcore tree:

```bash
make generate
go generate ./...
```

They work only when that compatible XML exists at the relative path above. In a normal standalone checkout, use the explicit-input workflow instead.

Normal build, unit-test, help, version, and schema workflows use the committed Go sources and do not require the XML:

```bash
make build
make test
go run . --help
go run . version --output json
go run . schema --groups
```

### Generated-file boundary and validation

Only object files in `cmd/generated/` that carry this header are emitted artifacts:

```go
// Code generated by splunkctl codegen. DO NOT EDIT.
```

Do not hand-edit those files. `cmd/generated/shared.go`, `_test.go` files, and `.gitkeep` are hand-maintained and must be preserved and reviewed normally.

For every XML, parser, generator, code-generation template, override-ownership, or generated-output change:

1. Record the immutable compatible splcore revision, XML SHA-256 digest, and stable non-sensitive input label.
2. Change the owning source, then run the explicit-input generator command.
3. Inventory every emitted file carrying the standard header. Compare the expected XML objects, same-name overrides, checked-in emitted files, and `cmd/register_generated.go`/`cmd/register_overrides.go`. If an XML object was removed or a full-object override was introduced, intentionally delete the stale emitted file and update registration; the generator will not do either.
4. Inspect the complete source and `cmd/generated/` diff. Confirm that every changed emitted object file is expected and that hand-maintained files were not treated as generator output.
5. After reviewing the initial source and artifact diff separately, capture a complete output-tree snapshot and second-run comparison without intervening edits:

   ```bash
   xml_path="REPLACE_WITH_STABLE_RELATIVE_XML_PATH"
   snapshot_dir="$(mktemp -d)"
   cp -R cmd/generated "$snapshot_dir/generated"
   go run ./codegen/ "$xml_path" \
       ./codegen/templates/command.go.tmpl \
       ./cmd/generated/
   diff -ru "$snapshot_dir/generated" cmd/generated
   ```

   This compares tracked, untracked, emitted, and hand-maintained contents, including additions and deletions. The temporary snapshot directory can be removed after the comparison. A clean comparison proves output-tree idempotence only; it does not prove that the emitted-artifact set is correct, so the inventory, stale-file, registration, and initial diff reviews remain required.
6. Include the source change and all affected emitted object files in the same MR.
7. Run the required final checks again:

   ```bash
   git diff --check
   make fmt-check
   go vet ./...
   make test
   make build
   go run . --help
   go run . version --output json
   go run . schema --groups
   ```

If the compatible XML is unavailable, stop and disclose the missing prerequisite. Do not edit emitted object files as a substitute or claim that regeneration was performed.

## Generator internals

```
codegen/main.go                        CLI entrypoint; reads args, loads template, iterates items
codegen/parser.go                      ParseXML() → []Item; maps XML structs to Go structs
codegen/generator.go                   BuildGeneratedFile(Item) → GeneratedFile; RenderFile() → gofmt'd []byte
codegen/templates/command.go.tmpl      Go text/template for one file
```

### XML → Go mapping

| XML element | Go output |
|---|---|
| `<item obj="index">` | file `cmd/generated/index.go`, top-level `IndexCmd` |
| `<common><uri>` | base REST path for all verbs on this object |
| `<cmd name="list">` | sub-command `IndexListCmd` with `RunE` |
| `<cmd><uri>` | per-verb URI override (falls back to common URI) |
| `<argsmap><arg cliname=... eainame=...>` | flag name → REST body key mapping |
| `<implied_arg_name>` | first positional arg (accepted as `--name` flag or `args[0]`) |
| `<eai_id>` | resource ID for single-resource ops: `{username}` = user-supplied, `server-settings` = literal |
| `<cmd:help><title>`, `<required>`, `<optional>` | Cobra `Short`, flag definitions |
| `<offline_ok />` | `Annotations: map[string]string{"offline_ok":"true"}` |

### Path template substitution

Some URIs contain `{varname}` placeholders (e.g. `/data/indexes/{name}/enable/`). The generator detects these via `reBraceVar` regex and:

1. Sets `VerbDef.PathHasTemplate = true` and `PathVarPlaceholder = "{name}"`
2. Emits `strings.ReplaceAll(path, "{name}", resourceID)` in the generated `RunE`
3. When the command also has an `ImpliedArg`, assigns `resourceID = impliedVal` so the placeholder is filled
4. Conditionally imports `"strings"` only in files that need it

### EaiID: user-supplied vs literal

XML `<eai_id>` can be:
- `{username}` — user supplies the value (braces = template variable)
- `server-settings` — hardcoded path segment (no braces = literal)

The generator sets `EaiIDLiteral = true` for literals so the template emits `resourceID = "server-settings"` rather than reading it from a flag.

### HTTP method inference

Derived from verb name in `parser.go:HTTPMethod()`:

| Verbs | Method |
|---|---|
| `list`, `show`, `display`, `status` | GET |
| `remove` | DELETE |
| everything else | POST |

### Override escape hatch

For a preferred full-object replacement, `cmd/override/<objectname>.go` makes codegen skip that object. The check uses `objectToFilename()` which converts `cluster-manager` → `cluster_manager.go`. The skip does not delete a previously emitted file, so the full replacement requires intentional stale-file removal and registration updates.

The checked-in `index`, `user`, and `scheduler` parents participate in legacy partial overlays wired explicitly by `cmd/register_overrides.go`. Codegen still skips these objects because same-name override files exist; it does not attach or replace their verbs. Changes to these overlays must audit the generated parent, override commands, registration, and artifact ownership together. New partial overlays require explicit design, registration tests, and a documented generator/artifact strategy.

### Template funcMap

| Function | Purpose |
|---|---|
| `title` | `"rolling-restart"` → `"RollingRestart"` (PascalCase, hyphen/underscore aware) |
| `goString` | wraps string in backtick string; falls back to `%q` if string contains a backtick |
| `escapeBacktick` | replaces backticks with apostrophes |
| `not` | negates bool or empty-string check (used in template conditionals) |

## Updating the generator

### Changing generated command behavior

Edit `codegen/templates/command.go.tmpl`, then re-run codegen. The template change and all affected emitted object files must be included together.

### Changing the data model

If you add fields to `VerbDef` or `GeneratedFile` in `generator.go`, update the template to use them, then re-run codegen and include the source and affected emitted object files together.

### Adding a new template function

Add to `funcMap` in `codegen/main.go`. Functions must be pure (no side effects) — they run during codegen, not at command runtime.

### Fixing an XML parsing issue

Edit `codegen/parser.go`. Tests are in `codegen/parser_test.go`. Run:

```bash
go test ./codegen/... -v -run TestParse
```

## register_generated.go

After codegen, registration must match the complete emitted-artifact inventory. Add each intended new `XxxCmd`; remove registrations for intentionally deleted full-replacement or removed objects; and audit the explicit partial-overlay wiring. Commands are organized into groups:

- **core** — visible in main help (index, app, user, role)
- **cluster** — visible under "Clustering Commands:" section
- hidden — superseded by override commands or low-value standalone; still callable directly
